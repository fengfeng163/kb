### Overview: what is Flow Designer?
![[Pasted image 20260819075941.png]]
Flow Designer is a Now Platform® feature that enables rich process automation capabilities in a consolidated design environment. It enables Process Owners and Developers to use natural language to automate approvals, tasks, notifications, and record operations without having to code.

> Important: Permission to use Flow Designer and view flow execution is controlled by assigning the flow_designer role to users. Before you give a Process Owner this role, understand that you are giving the user access to all tables and database operations which is equal to an admin role.

### Overview: Flow Designer Trigger
The trigger specifies the conditions that start the flow. When the trigger condition is true, the system starts the flow.
![[Pasted image 20260819082333.png]]

Creating a trigger for a flow requires configuring When to start the flow, Where to monitor for changes and What conditions must be met for this flow to start.

1. The Trigger dropdown has several Trigger Types to choose from.
- Record Trigger Type flows start when a record is newly created, updated, or both and if the transaction meets the condition filter. The Updated Trigger Type can run always or only once.
- Date (or Scheduled) Trigger Type starts a flow at a specific time of the day, week, or month. Also, a flow can start at a specific time and it will Run Once. If you need to set a flow to run at predefined intervals (example: every three days), use the Repeatchoice.
- Application Trigger Type has a MetricBase choice and a Service Catalog choice. MetricBase starts a flow by tracking time series data and can monitor when a threshold is reached, when a trend is detected or when a system stops reporting data. Service Catalog Trigger Type monitors all catalog item requests for a specific item.

Unlike Date (Scheduled) and Application Trigger Types, a Record Trigger Type requires:
1. Table to monitor - In this example, we have chosen the incident table as the place to look at for conditional changes. Choose the appropriate table.
2. Condition that starts the flow - Use the condition builder the same way you filter for a list. All conditions created in the condition builder must be met.

> **Tip from the Field**: You may not be able to use Application Trigger Type. The MetricBase Trigger Type requires a separate subscription. The plugin Flow Designer support for the Service Catalog (plugin Id: com.glideapp.servicecatalog.flow_designer) is active on new and upgraded instances.

### Overview: Actions
- A group of reusable operations that automate the Now Platform features without having to write code.
- Process Analysts can use Actions, Flow Logic, or Subflows.
![[Pasted image 20260819082926.png]]
Actions can be anything from creating tasks, looking up records, or sending email. Flow designer has many core actions that can be used and custom actions that can be created.
-  A core action is a ServiceNow-provided action available to any flow that cannot be viewed or edited from the Action Designer design environment.
- Custom actions can be viewed or edited from the Action Designer design environment. The custom actions always use the same configuration when added to a flow.

Flow Logic is a way to control what action steps are included or bypassed based or your criteria.
- The If conditional statements check if a condition is met before executing or skipping an action.
- The For Each Flow Logic loops through a list of records, supplied by flow data, to apply actions for each record that meets the condition specified. Creating a Nested For Each loop requires you to understand how many flow transactions this generates and its duration. Nested For Each loops are discouraged as they may cause the flow transaction quota rule to stop a flow after an hour.

Subflows are a sequence of reusable actions that can be started from a Flow, Subflow, or Script. Subflows are very similar to flows, but there are some differences.
- A trigger is not used to start a subflow.
- Subflows can use inputs from a parent flow.
- Subflows can return outputs to the parent flows when the subflows ends.

>Tip from the Field: Flows are set to allow 50 actions or less. You can increase the number of actions with the sn_flow_designer.max_actions system property, but performance may be impacted. Also, consider using Subflows for repetitive tasks used across multiple flows.

### Inline scripts
Enables users with coding experience to write inline scripts that set and modify input values during the configuration of an action or flow.
![[Pasted image 20260819083710.png]]

Inline scripts offers authorized users (admins, developers and those with the Allow Scriptingdelegated development permission) the ability to modify input values, such as small format conversions, data transformations, or math operations.

It is normally used when you need to write small and nonreusable logic. In case you need reusable code, create an action or subflow instead. If you decide to write an inline script it is important to remember that inline scripts must return values in the same data type as the input expects. For example, an inline script for a Date input must return a date-time value. Mismatches result in runtime errors.

Please note that before writing inline scripts you should be familiar with the Now Platform table structures and field types and how to work with record and system data using the ServiceNow API.

To toggle the feature on, select More Actions > User preferences > Show inline script toggle

### Complex data
- Provides an easy to understand, configurable, and graphical organization of complex structured data
- Allows structured data to be encoded and stored in a machine-readable format such as JSON or XML
![[Pasted image 20260819194045.png]]
Complex data allows you to encode and store structured data in a machine-readable format, such as JSON or XML. You can use the Flow Designer interface to view and understand the organization of structured data as well as create data structures.

With Complex Data you can:
- Parse and format data without having to write code.
- Create arbitrary data structures.
- View the organization of data structures.
- Allow access to data structure from API calls.
- Save and reuse data structures as templates.
- 
Since the data types in array and object variables are not Glide elements, there may not be complete compatibility between these items and Now Platform types.

An Array variable contains values for one data type. The child variable must be a single instance of a data type supported by the array.

An Object variable may contain any number of child variables which may have their own data types and values. This ability to nest Object variables allows you to create complex data structures analogous to a table schema where one table has related records in another table.

### Overview: Error Handler

- Enables flows to catch errors, and
- Runs a sequence of actions and subflows to identify and correct issues
![[Pasted image 20260819194207.png]]

Error Handler has the following components:
1. Error Handler switch – enables or disables flow error handling. When enabled, the Error Handler section is displayed.
2. Error Handler section – consists of the flow that runs when an error is identified. This section can be used to automate the identification and resolution of flow errors.
3. Error status – contains details about the error identified by the flow. These details are captured in Code (Integer) and Message (String) formats.

Error Handler, when enabled changes the states reported in the flow execution details.

-  Completed (error caught): indicates that an error was identified, and the Error Handler section flow ran successfully. It is generated even if the Error Handler Section is empty.
- Completed (error skipped): indicates that a custom action continued to run despite a step failure. When generated, the custom action passes the state to the parent flow.
- Error: indicates that an error remains uncaught. It either occurs:
	-  in the flow while the Error Handler is disabled
	-  or in the Error Handler section

> You can add up to 10 items in the Error Handler section, including actions, flow logic, or subflows.

### FlowAPI vs. FlowScriptAPI
![[Pasted image 20260819194359.png]]


#### FlowAPI methods
Use FlowAPI methods to execute actions, flows, or subflows in server-side scripts using either blocking or non-blocking methods.
#### FlowScript object
A FlowScriptAPI object allows you to access Flow Designer context details from script steps and inline scripts. You cannot instantiate objects of this type. Objects of this type are created automatically and are accessible only in script steps and inline scripts.

### ScriptableFlowRunner API call order
![[Pasted image 20260819195456.png]]
#### API call order
Build and execute flows, subflows, and actions using these APIs in the following order:
1. Create a builder object.
2. Specify Flow Designer content to run.
3. Retrieve Flow Designer execution details.

### ScriptableFlowRunner API call order example
![[Pasted image 20260819195541.png]]

#### API call order
Build and execute flows, subflows, and actions using these APIs in the following order:
1. FlowAPI: Creates a builder object.
Use getRunner() to instantiate the ScriptableFlowRunner builder object.
2. ScriptableFlowRunner: Specify Flow Designer content to run. Use these methods in the following order to create the builder pattern:
	1) Use one of the methods action(), datastream(), flow(), or subflow() to specify what type of Flow Designer object to build.
	2) Use one or more methods, such as addInput(), inDomain(), or quick() to specify execution parameters.
	3) Use the run() method to run the action, flow or subflow with the provided parameters and return a ScriptableFlowRunnerResult object.
3. ScriptableFlowRunnerResult: Retrieve Flow Designer execution details.
Use one or more methods such as getContextId(), getOutputs(), and getDomainId() to view execution details.

### GlideFlow API

Used for client-side interactions with Flows, Subflows, and Action
#### Client-side API
```
GlideFlow.startFlow(String <scoped_name>, Object inputs);
GlideFlow.startSubflow(String<scoped_name>, Object inputs);
GlideFlow.startAction(String <scoped_name>, Object inputs);
```
![[Pasted image 20260819195745.png]]

#### Client-side API
**Pros**: Allows front-end access to Flows/Subflows/Actions

**Cons**: Not immediate as JavaScript promise objects are returned which represents the eventual result of an asynchronous operation.

>**Note**: Server-side script is rigidly controlled compared to the Access to Client-side script. When using Client-side script to execute a Flow, Subflow, or Action, there must be a new “**client_callable_flow_object**” ACL type assigned to it. If this is not done, by default access will be denied. All ACL management is handled with the “Manage Security” menu in Flow Designer.
