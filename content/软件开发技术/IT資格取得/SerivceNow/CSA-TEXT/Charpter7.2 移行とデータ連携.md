## ユーザーストーリー
リリースマネージャーとして、システム管理者と連携してインスタンスから別のインスタンスに構成の変更を移行したいと考えています。そうすれば、ServiceNow プラットフォームでの更新をスムーズに実装することができます。

## アプリケーションスコープ
![[Pasted image 20260628221317.png]]
- アプリケーションスコープでは、使用可能なアーティファクトとデータへのアクセスを識別して制限することにより、アプリケーションを保護します。  
- アプリケーションスコーピング導入前に開発されたアプリケーションは、グローバルスコープ内にあります。  
- すべてのカスタムアプリケーションにはプライベートスコープが割り当てられ、アプリケーション自体と関連アーティファクトが一意に識別されます。  

管理者は、他のアプリケーションがカスタムアプリケーションレコードと各アプリケーションテーブルレコードからアクセスすることができる、アプリケーションの部分を指定できます。  

たとえば、会議室の予約アプリケーションをアプリケーションスコープで作成するとします。デフォルトでは、そのアプリケーションはアプリケーション自体のテーブルとビジネスロジックにアクセスして変更できますが、他のアプリケーションは、明示的な権限が付与されないかぎり、それらのテーブルやビジネスロジックにアクセスして変更することはできません。  

アプリケーションスコープにより、次の動作が保証されます。  
- 会議室予約アプリケーションによってコアサービスが中断されることはない  
- このアプリケーションの通常機能が他のアプリケーションによって妨げられることはない  

デフォルトでは、アプリケーションはアプリケーション自体のテーブルとビジネスロジックにアクセスして変更できますが、他のアプリケーションは、受け側のアプリケーションがアクセスを許可しないかぎり、それらのテーブルやビジネスロジックにアクセスして変更することはできません。アプリケーションスコープによって名前の競合が防止されるとともに、コンテキスト依存型開発環境で、どの変更が許可されるかを判断できます。アプリケーション開発者は、アプリケーションを作成するときにアプリケーションスコープを指定します。  

グローバルスコープは特別なアプリケーションスコープで、アプリケーションスコーピングより前に開発されたアプリケーションや、他のすべてのグローバルアプリケーションからアクセスできるようにすることを意図されたアプリケーションを識別します。  

システムにより、テーブル、スクリプト、および設定レコードなどのアプリケーションアーティファクトの先頭に名前空間識別子が付加されます。

## システム更新セット
![[Pasted image 20260628221537.png]]

更新セットとは、以下を含む XML ファイルです。
• 更新セットを一意に識別するレコードセットの詳細
• 構成変更のリスト
• 別のインスタンスが構成変更を取得して適用できるかどうかを決定するステータス

更新セットは、アプリケーションとシステムプラットフォームの機能に対する変更を追跡します。これにより、開発者は非本番インスタンスで新しい機能を作成し、別のインスタンスに変更を反映させることができます。

基本的に更新セットレコードは、プロセスレコードの「特定の時点での」XML スナップショットです。更新セットは、追跡されるテーブルから Customer Update [sys_update_xml] テーブルに変更を書き込むことによって機能します。

更新セットは、別のインスタンスでチェックおよび検証された変更を適用するために使用します。複数の更新セットを結合するときに、いくつかの更新セットで同じオブジェクト (インシデントフォームなど) に変更が加えられている場合は、最後に行われた変更が結合後の新しい更新セットに移されます。

更新セットは設定レコードのコンテナーです。[All] > [System Update Sets] > [Local Update Sets] に移動することにより、新しい更新セットを作成したり、既存の更新セットを現在の更新セットに設定したりすることができます。更新セットを使用してコードを移行します。更新セットが作成されたら、別のインスタンスに移送して、開発からテスト、本番に至るまで、カスタマイズを移動できます。  

デフォルトの更新セットは、ユーザーが作成した更新セットに変更を加えることなく、インスタンスに行われた変更をキャプチャします。カスタマイズをインスタンス間で移動する場合は、デフォルトの更新セットを使用しないことをお勧めします。代わりに、名前付き更新セット (ユーザー作成) を使用してください。  

**更新セットのバッチ**を使用すると、更新セットをグループ化して一括でプレビューおよびコミットできます。  

複数の更新セットを処理すると問題が発生する場合があります。たとえば、更新セットを正しくない順序でコミットしたり、1 つまたは複数の更新セットを誤って除外してしまったりする可能性があります。更新セットをすべてバッチにグループ化すれば、このような問題を回避できます。  

更新セットのバッチの詳細については、ServiceNow 製品ドキュメント『更新セットの一括』を参照してください。

## 更新セットに取得される情報
![[Pasted image 20260628221909.png]]

通常、更新セットにはカスタマイズや構成変更の情報が取り込まれており、データレコードに対する変更は含まれていません。たとえば、更新セットの追跡レポートの定義や、データソース、レポートタイプ、スタイル、共有設定といった関連データです。ただし、実際のデータとレポート出力が更新セットで追跡されることはありません。これらは更新セットに含まれているものと含まれないものの一例であり、すべてを網羅しているわけではありません。  

メモ：データは更新セットに取得されません。例 : 新規インシデントまたは新規変更レコードは、更新セットに含まれません。  

作業が完了したら、更新とともにデータレコードを移動することができます。これらのレコードは、テストやトレーニングで便利に使用できます。データ (ユーザーレコード、CI、場所など) は [Export XML] 機能を使用して移動できます。  

メモ：ダッシュボードタブに関連するポータルページは、自動的には更新セットに含まれません。Unload Dashboard 機能を使用して、ダッシュボードレコードから更新セットにポータルページを追加できます。Unload Dashboard 機能は、ポータルページなどのすべての関連タブとともにダッシュボード全体をアンロードします。  

このプロセスの詳細については、ServiceNow 製品ドキュメント『Move a dashboard with an update set』を参照してください。

## 更新セットの作成と選択
![[Pasted image 20260628222117.png]]

- [All] > [System Update Sets] > [Local Update Sets] に移動して、[New] をクリックします。
-  テーブルのフィールドのフォームに入力します。
-  [Submit] をクリックして更新セットを作成します。

![[Pasted image 20260628222144.png]]

管理者としての考え方 : 更新セットには識別しやすくなるような名前を付けてください。イニシャルやストーリー番号で関連性を持たせたり、いくつかのキーワードで更新セットの内容を定義したりすることができます。

更新セットのステータスの詳細については、ServiceNow 製品ドキュメント『更新セットを現在のセットとして作成し選択する』を参照してください。

## 更新セットを完了としてマーク

設定が完了したら、競合解決のためのローカル更新セットの比較確認を行い、更新セットを [Complete] としてマークします。

![[Pasted image 20260628222244.png]]

- 更新セットのレコードを開きます。
- 更新セットの [State] を [Complete] に変更します。

更新セットは、他のインスタンスで取得できます。
追加のカスタマイズは更新セットでは追跡されません。

移行の準備が整っている場合にのみ、更新セットを [Complete] としてマークします。更新セットの完了後は、[In progress] に変更しないでください。代わりに、残りの変更のために別の更新セットを作成します。作成された順にまとめてコミットしてください。この場合、命名規則が役に立つことがあります (例 : Performance Enhancements と Performance Enhancements 2)。
