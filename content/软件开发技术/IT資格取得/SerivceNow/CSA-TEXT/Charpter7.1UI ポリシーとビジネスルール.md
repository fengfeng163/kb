## ServiceNow でのスクリプティングとは ?
![[Pasted image 20260628082559.png]]

**クライアント**は、リモートサービスや他のコンピューターシステム (サーバー) にアクセスするアプリケーションまたはシステムです。**サーバー**は、サービスとして実行されるコンピュータープログラムのことで、1 つ以上のサービスを実行する専用の物理コンピューターか、データベースを実行するシステムを指します。

ServiceNow では aPaaS (Application Platform as a Service) モデルを使用しており、Web ブラウザはクライアントとなります。Web ブラウザは、クライアントへのインストールが必要な唯一の構成要素です。アプリケーションサーバーとデータベースはデータセンターで稼働します。クライアントサイドのスクリプトはクライアントブラウザで実行されます。サーバーサイドのスクリプトは (データベースが組み込まれている) サーバーで実行されます。

クライアントとサーバー間の往復には時間がかかり、エンドユーザーは往復が完了するまで待つ必要があります。往復には、要求 (リクエスト) と応答 (レスポンス) が含まれます。

**メモ** : ノーコードの代替手段で同じ目標を達成できる場合は、それらを代わりに使用してください。

## ServiceNow のスクリプティング領域

ServiceNow には、プラットフォームの基本動作を変更するためにコードを挿入できる場所が 30 か所以上あります。
![[Pasted image 20260628153049.png]]

JavaScript は、Webの主要なクライアントサイドスクリプト言語です。最近の大半の Web ブラウザに組み込まれていることで知られ、非常に柔軟で強力な言語です。このため、今日の Web 開発において JavaScript はほとんど必須のスキルとなっています。構文が簡単なため、多くの人が最小限の努力で簡単にロジックを Web ページに追加できるようになります。この使い慣れた言語の利点を活かし、ServiceNow ではサーバーとクライアントの両方で JavaScript を使用しています。このモジュールでは、ハイライトされた概念について説明します。  

スクリプティングの詳細については、ServiceNow 製品ドキュメント『スクリプティング』を参照してください。ServiceNow Developer サイトで他のリソースも参照してください。

## ポリシー、アクション、ルール、スクリプトのサンプル
![[Pasted image 20260628153316.png]]
その他の例 :

• ビジネスルール : 通知をトリガーするだけでなく、他にも多くのことを実行できます。たとえば、レコードやフィールドに変更が加えられた際に、その他のアクションをトリガーさせることもできます。基本的な例としては、親インシデントで何かが起こった場合に子インシデントを更新するビジネスルールなどが考えられます。

• クライアントスクリプト : ポップアップメッセージを表示するだけでなく、他のことも実行できます。クライアントスクリプトで多い実装例としては、別フィールドの値の変更に対応してフィールドの値を変更するものです。たとえば、次のようになります。アサイン先グループの値が更新された際、[Assigned to] が新しいアサイン先グループのメンバーでない場合は、クライアントスクリプトが [Assigned to] フィールド値を消去するように実装できます。

• データポリシー : 必須フィールドだけでなく読み取り専用フィールドも設定することができます。そのため、インポート時またはスクリプト/ユーザーによって入力された時に、データ操作がされないようにすることができます。さらに、リストにおいても動作します。

## データポリシー
![[Pasted image 20260628154545.png]]

データポリシーにより、ServiceNow にデータが挿入されたとき、または外部システムを通じてインポートセット内のデータが送信されたときに、フィールドやレコードデータで強制的に要件が満たされるようにします。データポリシーは、Web サービスやインポートセットの場合には適用されないようにすることができます。データポリシーを使用して、フォームフィールドの状態を必須と読み取り専用に設定できます。データポリシーをリストに適用してフィールドを読み取り専用にすることができます。フィールドは編集できるように見えますが、更新を試みても失敗します。  

データポリシーの目的は、すべての ServiceNow アプリケーションにおいて同じデータを標準化することです。  

**メモ**：データポリシーはセキュリティに関するものではなく、データベースに格納された情報の整合性を管理するものです。データポリシーを定義すると、UI からレコードが送信されるときにポリシーが適用されます。この動作を変更することはできません。

## UI アクション
![[Pasted image 20260628160510.png]]
UI アクションには、カスタム機能を定義するスクリプトを含めることができます。UI アクションは、[Client] チェックボックスのオン/オフを切り替えることにより、サーバーサイドまたはクライアントサイドに設定することができます。この設定により、UI アクションが表示されるタイミングが決まります。

UI アクションには次のようなものがあります。
• フォームボタン
• フォームコンテキストのメニュー項目 (ヘッダーを右クリック)
• フォームリンク (フォーム内の関連リンク)
• リストボタン
• リストコンテキストのメニュー項目 (レコードの右クリック)
• リストの選択肢 (リスト下部)
• リストのリンク (リスト下部の関連リンク)

[Order] を 100 に指定すると、ユーザーインターフェイスでは、[Order] の数字が 100 より大きい UI アクションがこの UI アクションの後に表示されるのに対し、[Order] の数字が 100 未満の UI アクションはこの UI アクションの前に表示されます。

**メモ** : UI アクションの [Active] ボックスをオンにすると、その UI アクションが表示され、ユーザーが操作できるようになります。

**ヒント** : [Save] ボタン/UI アクションを有効にするには、[All] > [System Properties] > [UI Properties] の順に移動して、[Show “Save”, “Insert”, and “Insert and Stay” buttons on forms] を選択します。

## クライアントスクリプト

![[Pasted image 20260628160940.png]]
クライアントスクリプトにより、条件付きでフィールドを表示するといった操作や検証処理をブラウザやフォームで実行できます。ユーザーがインシデントの優先度を変更したときにアラートが表示されるようにする動作は、この一例です。クライアントスクリプトはブラウザで実行されますが、データベースのルックアップが必要な場合にもクライアントスクリプトを実行できます。データベースの情報が必要で、その情報が頻繁に (たとえば、フォームをロードするたびに) 必要になる場合には、それがフォームに追加できても非表示になっているフィールドなのか、そのフィールドは本当に必要なのかを検討してください。

次のいくつかのタイプのスクリプトがサポートされています。  
- onCellEdit() : リストエディターを使用してリストのセルの値が変更されると実行されます。  
- onChange() : 特定のフィールドの値が変更されると実行されます。  
- onLoad() : フォームがロードされると実行されます。  
- onSubmit() : フォームが送信されると実行されます。

onLoad() や onSubmit() スクリプトとは異なり、onChange() スクリプトは、フォーム自体ではなくフォーム上の特定のフィールドに適用されます。それらのスクリプトは、フォーム上の特定のフィールドに変化があると実行されます。   

onLoad() スクリプトは、フォームが初めて表示されるとき、コントロールがユーザーに移動して入力可能になる前に実行されます。通常、onLoad() スクリプトは、画面上のドキュメントで何らかのクライアントサイドの操作を実行するために使用します。

onSubmit() スクリプトはフォームの送信時に実行されます。通常、onSubmit() スクリプトは、フォームの内容を検証して送信可能なことを確認するために使用します。そのため、onSubmit() スクリプトを実行すると、false が返されて送信がキャンセルされる可能性があります。

## スクリプトタイプ : ビジネスルール

ビジネスルールは、レコードが表示、挿入、更新、削除されたとき、またはテーブルに対してクエリーがあったときに実行されるように設定できます。

![[Pasted image 20260628162033.png]]

![[Pasted image 20260628162049.png]]

ServiceNow アプリケーションでの動作は複数の方法で制御できますが、プラットフォームの動作のカスタマイズでは、ほとんどの場合にビジネスルールが使用されます。ビジネスルールは、ユーザーとプラットフォームの間の毎回のやりとりの最初にロードされて初期化されます。すべてのビジネスルールは、(スコープ対象のアプリケーションでスクリプティングするときにスコープ付き API を使用する) アプリケーションスコープまたはグローバル環境 (アプリケーションスコーピングより前に開発されたアプリケーションや、他のすべてのグローバルアプリケーションからアクセスできるようにすることを意図されたアプリケーションを識別するアプリケーションスコープ) のいずれかにアサインされます。  

すべてのビジネスルールには、実行対象のテーブルとタイミング (挿入の前後など)、評価する条件、評価に基づいて実行するスクリプトが定義されています。  

ビジネスルールは、フォーム、リスト、または Web サービスからのアクセス方法に関係なく、一貫してレコードに適用されます。フォーム、リスト、または Web サービスからのアクセス方法に関係なくビジネスルールが適用されるのに対して、クライアントスクリプトはフォームでフィールドが変更される場合にのみ適用される点が、ビジネスルールとクライアントスクリプトの間の主な違いです。 

UI ポリシーとは異なり、ビジネスルールは次のようにリアルタイムではありません。  
- フォーム上のフィールドを監視しません。  
- レコードが挿入または更新されるときにレコードを監視します。  

表示ビジネスルールの主な目的は共有されるスクラッチパッドオブジェクト「g_scratchpad」を使用することです。このオブジェクトはフォームの一部としてクライアントにも送信されます。この動作は、表示されるレコードには含まれていないサーバーデータを必要とするクライアントスクリプトを作成する場合に役立ちます。  

**メモ**：**ビジネスルールをスクリプティングする前に、Flow Designer で同じ目標を実現できるかどうかを検討してください。**
