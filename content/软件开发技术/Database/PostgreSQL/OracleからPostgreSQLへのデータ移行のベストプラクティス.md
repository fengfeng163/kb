OracleからPostgreSQLへの移行は、データ・コード・パフォーマンスなど多層にわたる複雑なシステムプロジェクトです。以下、実務で検証されたベストプラクティスを紹介します。

## 一、移行前の評価フェーズ

**1. 互換性評価**

専門ツールでソースDBを全面的にスキャンし、移行の難所を特定します。

- **Ora2Pg**：オープンソースの定番。詳細な移行評価レポート（migration cost）を生成し、1～1000点で移行難度を定量化
- **AWS SCT (Schema Conversion Tool)**：無料で、クラウド利用しない場合でも評価に使用可能
- **EDB Migration Toolkit**：EnterpriseDB社の商用ツール、大企業向け

評価で重点的に確認すべき項目は、ストアドプロシージャ／パッケージ（PL/SQL）の数と複雑度、特殊データ型（`LONG`、`RAW`、`BFILE`、ネストテーブルなど）、データベースリンク（DB Link）、マテリアライズドビュー、パーティションテーブル、トリガー、シーケンスです。

**2. 容量とパフォーマンスのベースライン**

Oracleの現行のデータ量、TPS/QPS、スロークエリ、主要業務のレスポンスタイムSLAを記録し、移行後の比較基準とします。

## 二、スキーマとオブジェクトの移行

**1. データ型のマッピング**

|Oracle|PostgreSQL|注意点|
|---|---|---|
|`NUMBER`|`NUMERIC` / `BIGINT` / `INTEGER`|精度指定なしのNUMBERは実態に合わせて整数型を選択|
|`VARCHAR2(n)`|`VARCHAR(n)`|PGの長さは文字単位|
|`DATE`|`TIMESTAMP(0)`|OracleのDATEは時分秒を含む|
|`CLOB`|`TEXT`|PGのTEXTは長さ制限なし|
|`BLOB`|`BYTEA` または `Large Object`|1GBを超える場合はLO|
|`RAW`|`BYTEA`||
|`NUMBER(1)` をBOOL用途|`BOOLEAN`|業務的な意味の確認が必要|

**2. 重点的な改修対象**

- **シーケンス**：Oracleの `seq.NEXTVAL` をPGの `nextval('seq')` に変更、または `IDENTITY`/`SERIAL` を使用
- **ストアドプロシージャ／パッケージ**：PL/SQLをPL/pgSQLに変換。パッケージ変数や自律トランザクション（PGはネイティブ非対応のため、dblinkやバックグラウンドワーカーで代替）に注意
- **階層クエリ**：`CONNECT BY` を `WITH RECURSIVE` 再帰CTEに変換
- **分析関数**：大部分は互換性あり。ただし `(+)` 外部結合構文は標準の `LEFT/RIGHT JOIN` に変更が必要
- **MERGE**：PG 15以降ネイティブ対応。それ以前のバージョンでは `INSERT ... ON CONFLICT` を使用
- **シノニム**：PGにネイティブのシノニムは存在しないため、`SEARCH_PATH` やビューで代替
- **DBLink**：`postgres_fdw` または `dblink` 拡張を使用

## 三、データ移行戦略

**停止可能時間（ダウンタイム）**と**データ量**に応じて適切な方式を選択します。

**方式A：停止一括移行（中小規模データ・停止許容ケース向け）**

データ量が数百GB以下、数時間の停止が可能な場合に適しています。フローは「業務停止 → 全量エクスポート → PGへインポート → 検証 → 切替」となります。

ツール推奨：Ora2Pg（COPYファイルを直接生成）とPGの `COPY` コマンドの組み合わせ。`INSERT` より10倍以上高速です。

**方式B：全量＋差分（大規模データ・短時間停止向け）**

1. まず全量データの初期化を実施（業務稼働中に実行可能）
2. CDCツールで差分を捕捉：**Oracle GoldenGate**（商用、最も安定）、**Debezium + Kafka**（オープンソース主流）、**DSG**、**StreamSets**
3. 差分を継続同期し、追いつくまで継続
4. 短時間停止して切替、検証後にトラフィック移行

**方式C：ダブルライト・グレーリリース（金融等高可用性ケース向け）**

アプリケーション層からOracleとPGの両方に同時書き込みし、読み込みトラフィックをOracleからPGへ段階的に切替。一定期間観察後にOracleを廃止します。最も安全ですが、改修コストが最大です。

## 四、アプリケーション層の改修

**1. SQL互換性の改修**

書き換えが必要な箇所として、`ROWNUM` → `LIMIT/OFFSET` または `ROW_NUMBER()`、`SYSDATE` → `CURRENT_TIMESTAMP` または `now()`、`NVL` → `COALESCE`、`DECODE` → `CASE WHEN`、`DUAL` テーブル（PGではFROM句省略可）、空文字列とNULLの違い（Oracleは空文字列をNULLとみなすが、PGはみなさない、これが**最も陥りやすい落とし穴**）などがあります。

**2. ORMとコネクションプール**

MyBatis/Hibernateを使用している場合、ダイアレクト設定と一部のネイティブSQLの修正が必要です。コネクションプールパラメータ（HikariCPなど）も再チューニングが必要で、PGはコネクション生成コストが高いため、**PgBouncer** をコネクションプールプロキシとして併用することを推奨します。

**3. トランザクションと分離レベル**

Oracleはデフォルトで READ COMMITTED ですがマルチバージョンスナップショットで実装されており、PGも MVCC ですが実装の詳細が異なります。`SELECT FOR UPDATE` の挙動差異や、長時間トランザクションがPGに与える悪影響（vacuumが回収できない）に注意が必要です。

## 五、テストと検証

**1. データ整合性検証**

- 行数比較：各テーブルの `COUNT(*)` を照合
- サンプリング検証：主要業務テーブルの全フィールドハッシュ比較（MD5集約など）
- 重要指標：財務集計値、注文総額など業務レベルの検証

**2. パフォーマンステスト**

- フルリンク負荷試験で主要APIのP99レイテンシを比較
- 複雑なSQLのPG上での実行計画を重点的に確認。インデックス再構築やSQL書き換えが必要な場合あり
- PGオプティマイザは統計情報に敏感なため、移行後ただちに `ANALYZE` を実行

**3. グレーリリース**

ユーザー／テナント／地域単位で段階的に切替を実施し、迅速なロールバック手段を確保しておきます。

## 六、本番稼働後の運用

- **パラメータチューニング**：`shared_buffers`（物理メモリの25%推奨）、`effective_cache_size`、`work_mem`、`maintenance_work_mem`、`wal_buffers`、`max_connections`
- **VACUUM戦略**：適切なautovacuumパラメータを設定し、テーブル肥大化を防止
- **監視体制**：`pg_stat_statements`、Prometheus + postgres_exporter、pgBadgerによるスロークエリ分析を活用
- **高可用性**：ストリーミングレプリケーション + Patroni/repmgr で自動フェイルオーバーを構築
- **バックアップ**：`pg_basebackup` + WALアーカイブ、または pgBackRest

## 七、重要なリスクポイント

1. **空文字列問題**：Oracleでは `''` がNULLと等価ですが、PGでは空文字列のままです。業務ロジックに不具合が出る可能性があるため、全コードのスキャンが必須
2. **大文字小文字の扱い**：PGはオブジェクト名がデフォルト小文字、Oracleはデフォルト大文字。クォート付き識別子のSQL移植には特に注意
3. **暗黙的な型変換**：PGはOracleよりはるかに厳格。例えば `WHERE int_col = '123'` がPGではエラーになる場合あり
4. **PL/SQL例外処理**：エラーコードと例外名が異なるため、一つずつマッピングが必要
5. **文字セット**：UTF-8に統一。Oracleの `NLS_LENGTH_SEMANTICS` 設定にも注意

---

**実務的アドバイス**：移行プロジェクトは通常、作業量の70%がPL/SQL改修とSQL互換性問題に費やされ、データ移送そのものではありません。まずOra2Pgで評価レポートを実行して全体像を把握し、段階的に進めることをお勧めします。**非コアシステムから着手して経験を積み**、最後にコアトランザクションシステムを処理するのが定石です。PL/SQLが極めて複雑で改修コストが高すぎる場合、Oracle構文の大部分と互換性のある **EDB Postgres Advanced Server** を移行期の選択肢として検討する手もあります。
